# Security headers and Content-Security-Policy (#42)

Every response from `apps/web` — HTML pages, the MCP endpoint, the chat stream, and the other
`/api/*` routes — carries a reviewed set of HTTP security headers, defined once in
`apps/web/src/lib/security/build-security-headers.ts` and applied by `apps/web/middleware.ts` on
every request. The header set is split into two route groups because a browser document and a
JSON API need different things:

- **HTML route group** — every page under `apps/web/app/**` (and the handful of non-HTML document
  routes: `/llms.txt`, `/llms-full.txt`, `/manifest.webmanifest`, `/robots.txt`, `/sitemap.xml`,
  `/.well-known/mcp.json` — the CSP is harmless on these, browsers only enforce it on documents).
- **API/MCP route group** — everything under `/api/*`: `/api/mcp`, `/api/chat`, `/api/stats`,
  `/api/cron/*`.

This is the same policy an automated test locks in (`middleware.test.ts`,
`src/lib/security/build-security-headers.test.ts`,
`apps/web/e2e/security-headers.smoke.spec.ts`, `apps/web/mcp-e2e/security-headers.spec.ts`,
`apps/web/e2e-preview/specs/security-headers.spec.ts`) — a change to any value here must change
those tests too, on purpose, not as a side effect.

## HTML route group

| Header | Value | Why |
| --- | --- | --- |
| `Content-Security-Policy` | `default-src 'self'; script-src 'self' 'nonce-<per-request>' 'strict-dynamic'; style-src 'self' 'nonce-<per-request>'; img-src 'self'; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests` | Enforcing, not report-only. No `unsafe-inline`/`unsafe-eval` anywhere. Every fetch directive is `'self'` — see "Why there is no external origin" below. `strict-dynamic` lets Next's own nonce'd hydration script propagate trust to scripts it inserts at runtime (Vercel Analytics' `/_vercel/insights/script.js`, appended via `document.createElement` from inside the already-trusted app bundle) without allowlisting an origin for it. `frame-ancestors 'none'` — this site is never meant to be framed by anyone, including itself. `upgrade-insecure-requests` is defense-in-depth; every asset is already same-origin HTTPS. |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | See "HSTS, and why it's mostly moot here" below. |
| `X-Content-Type-Options` | `nosniff` | Stops a browser from MIME-sniffing a response into an executable type it wasn't served as. Costs nothing, no reason to omit it anywhere. |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | Sends the full URL as referrer to same-origin requests (useful for internal analytics), only the origin cross-origin, nothing over plain HTTP. The browser-default-safe baseline. |
| `X-Frame-Options` | `DENY` | Belt-and-suspenders with `frame-ancestors 'none'` for the (much larger) population of tools that still only read the legacy header. |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=(), usb=(), browsing-topics=()` | Denies every browser feature this static/portfolio site has no use for, including opting out of Topics/FLoC-style tracking regardless of what an embedding context might otherwise grant. |

### Why there is no external origin to allowlist

The issue asked to enumerate every third-party origin actually in use, and to prefer removing an
origin over allowlisting it. An audit of the codebase found none needed removing, because none are
used:

- **Fonts** — `app/fonts.ts` uses `next/font/google`, which downloads and self-hosts the font
  files at build time; the browser never requests anything from `fonts.googleapis.com` or
  `fonts.gstatic.com`. `font-src 'self'` is correct as-is.
- **Analytics** — `@vercel/analytics/next` (`app/design-system/analytics/site-analytics.tsx`)
  beacons to this deployment's own `/_vercel/insights/script.js`, first-party and cookieless. No
  `connect-src`/`script-src` entry needed beyond `'self'` (plus `strict-dynamic`, see above).
- **Chat and MCP** — the chat widget streams from `POST /api/chat` and the `/mcp` page's demo
  client talks to `POST /api/mcp`, both same-origin. `connect-src 'self'` covers both.
- **Images** — no `next/image` remote loader is configured and no component references an
  external image URL; every icon/OG image is generated by this app's own routes. `img-src 'self'`
  needs no `data:`/`blob:` addition — nothing in the codebase emits a `data:` image URI.

If a future epic adds a genuine third-party origin (e.g. a CDN-hosted asset), add it to the
specific directive it belongs to — never widen `default-src`.

### The nonce mechanism

Per [Next.js's own CSP guide](https://nextjs.org/docs/app/building-your-application/configuring/content-security-policy)
(not a third-party blog post — those are commonly stale for this exact topic), `apps/web/middleware.ts`
generates a fresh, cryptographically random nonce per request, embeds it in the CSP's `script-src`
and `style-src`, and forwards it two ways: as the `x-nonce` request header (read by Server
Components via `src/lib/security/get-request-nonce.ts`'s `getRequestNonce()`) and as the `x-nonce`
response header (inspectable without re-parsing the CSP value). Next.js detects this same nonce
from the CSP response header and applies it automatically to the inline scripts it generates
itself (the streaming hydration payload); this app's own two inline scripts —
`app/layout.tsx`'s theme-flash guard and `src/lib/seo/json-ld-script.tsx`'s structured-data
`<script type="application/ld+json">` tags (rendered on `/`, `/projects/[slug]`,
`/writing/[slug]`) — read the nonce explicitly and pass it through.

One consequence worth recording: nonce-based CSP requires per-request dynamic rendering (a static
build can't embed a nonce that's only known at request time — this is explicit in Next's own
docs). `/projects/[slug]` and `/writing/[slug]` already read other per-request data, but calling
`headers()` for the nonce is what makes Next render them dynamically rather than prerendering them
at build time (confirmed in `apps/web/.next/prerender-manifest.json` after a production build —
only their `opengraph-image` sub-routes remain statically prerendered, the pages themselves do
not). This is the correct trade-off for a CSP that's actually enforcing rather than theatre; it's
called out here so a future contributor investigating a build-output change knows why.

## API/MCP route group

| Header | Value | Why |
| --- | --- | --- |
| `Content-Security-Policy` | `default-src 'none'; frame-ancestors 'none'` | These routes only ever return JSON — never an inline script, stylesheet, or frame — so `'none'` is strictly more restrictive than the HTML policy, not a relaxed variant of it. No nonce needed; nothing here is ever parsed as HTML. |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | Same value and same reasoning as the HTML group — transport security is a property of the origin, not the route. |
| `X-Content-Type-Options` | `nosniff` | Same reasoning as the HTML group. |
| `Referrer-Policy` | `no-referrer` | Stricter than the HTML group's default: a JSON endpoint has no legitimate reason to leak the calling page's URL to anywhere, including this origin's own logs. |
| `X-Frame-Options` | `DENY` | These are never meant to be loaded in a `<frame>`/`<iframe>` either. |
| `Cache-Control` | `no-store` | Every response in this group is either per-caller (`/api/mcp`, `/api/chat` — see the MCP tool-call and chat-stream responses) or privileged (`/api/stats`, `/api/cron/*`) and none of the underlying handlers set their own caching directive today, so applying this uniformly is safe and closes the gap rather than opening one. |

No `Permissions-Policy` — that header is only evaluated by a browser rendering an HTML document
with an embedded/iframed context; it has no meaning for a JSON response a browser never renders.

The MCP endpoint (`/api/mcp`) keeps passing a full `initialize` → `tools/list` → `tools/call`
sequence with every one of these headers enforced — see
`apps/web/mcp-e2e/security-headers.spec.ts` (a real, locally started `next start` server, the same
black-box harness `protocol.spec.ts` uses) and
`apps/web/e2e-preview/specs/security-headers.spec.ts` (the same sequence against a real deployed
preview).

## HSTS, and why it's mostly moot here

`Strict-Transport-Security: max-age=31536000; includeSubDomains` (one year, `includeSubDomains`,
**no** `preload`) — reasoned against the actual deployment, not a generic recommendation:

- **#33 closed with no custom domain.** This deployment is reached only at
  `hire-me-mcp-web.vercel.app` — there is no subdomain to worry about locking out, and no DNS/TLS
  configuration this header could interact badly with.
- **`.app` is already HSTS-preloaded at the gTLD level.** Google, as the `.app` registry, requires
  HTTPS for every `.app` registration and the entire TLD ships on browsers' built-in HSTS preload
  list. That means every major browser already refuses a plaintext `http://hire-me-mcp-web.vercel.app`
  request and upgrades to HTTPS *before this header, or any response at all, is ever read* — the
  header cannot add any protection a browser doesn't already provide for this specific host.
- **It's set anyway**, for three reasons that survive that fact: (1) it's what security scanners
  (Mozilla Observatory, securityheaders.com) and a defense-in-depth baseline expect to see, so its
  absence would read as an oversight rather than a reasoned decision; (2) not every HTTP client is
  a browser that special-cases the `.app` TLD preload list — a non-browser client that does talk
  plain HTTP once still benefits from the header on the redirect response; (3) it costs nothing and
  removes no capability.
- **`includeSubDomains` is safe to set now**: no subdomain of `hire-me-mcp-web.vercel.app` exists
  or is served by this project, so there is nothing for it to lock out — the usual danger
  (`includeSubDomains` breaking a subdomain that turns out to need plain HTTP) doesn't apply.
- **`preload` is deliberately withheld.** Submission to the browser HSTS preload list is
  effectively irreversible in practice (removal can take months to over a year to propagate) and
  is meant for a domain whose hosting is final. Per #33, this one explicitly is not — a future
  custom domain would need its own, separately reasoned `preload` decision made once that domain
  and its HTTPS setup are actually final, not this one carried over by default.

In short: **the `includeSubDomains`/`preload` decision the issue asks for is real, but its
practical effect on `hire-me-mcp-web.vercel.app` today is close to zero**, because the `.app` TLD's
own preload coverage already does the enforcement this header exists to provide. That's recorded
explicitly here rather than left implicit, per the task's instruction not to treat it as settled by
default.
